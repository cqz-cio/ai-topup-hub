## 固定恢复边界

正式服务使用以下三个环境变量；上线前保留采购关闭，在服务停止后记录订单最大 ID 与 UTC 恢复时刻，再以同一受保护的新程序一起启用：

- `UPSTREAM_PURCHASE_ENABLED=true`。
- `UPSTREAM_PURCHASE_ORDER_ID_FLOOR`：停止旧服务后数据库中已有订单的最大 ID，包含父子订单和未付款旧订单。
- `UPSTREAM_PURCHASE_PAID_AFTER`：恢复时刻，带时区的 RFC3339 格式。

新父单和子单的 ID 均须超过边界，付款时间严格晚于恢复时刻；采购任务也须创建于恢复后。历史订单即使收到迟到回调，也不能通过 ID 校验。重启及后续发布必须原样保留此边界，不能每次重启重设时间，也不能删除边界后保留采购开启。

两项边界配置只给一项、为空或无效时，程序拒绝启动，不退回无限制采购。未配置两项的其他部署保持原行为。应用服务复制边界配置，避免调用方修改影响运行中的许可。

## 采购入口约束

在创建采购意图、队列提交和重试之前核对边界；后台人工重试历史订单直接拒绝，保留原记录。历史队列投递安全结束，不修改采购状态，不连接供应商，不再次入队。重启恢复查询先筛掉历史记录再分页，避免大量旧任务挡住新订单。

新订单沿用现有付款确认、采购唯一约束、供应商持久化提交认领和发卡流程。请求结果不明时仍转人工核对，不能盲目重试。拆单允许父单部分交付后继续处理其余已付款子单。既有已接受采购的只读查单不发送采购请求。

恢复后的新采购若已接受，但进程在本地发卡和最终采购状态之间中断，恢复任务仍可继续只读查单并完成记账；本地已交付状态不会阻断该恢复，也不会触发再次采购。历史订单的时间及 ID 边界对这一路径同样有效。

SQLite 查询按绝对时间比较 UTC 与带偏移的 `paid_at`，应用层再次核对精确时间。恢复边界不会写入业务订单、钱包、采购和支付表。
