## 触发与结束

商品付款前检查发现 `card_platform_insufficient_balance` 时，除了原有商家提醒，新增一条 `supplier_balance_waits` 等待记录。记录以商城父订单 ID 唯一，保存客户邮箱、商品名称、订单号和该订单按卡台汇总的采购成本快照。父子订单不重复计算，人工及本地发货商品仍不需要卡台余额。

客户记录不依赖商家邮件是否发送成功，也不受商家提醒 30 分钟冷却影响。关闭网页、队列临时故障及程序重启不会清除已保存的等待。只从功能启用后的付款拦截登记，不追溯补发历史订单。

`storefront` 和普通 `worker` 模式注册 `supplier_balance:poll`，间隔固定 60 秒；`checkout` 受限模式不新增轮询。没有有效等待时不访问上游。有等待时每轮每个卡台只读取一次余额，多笔订单共用查询结果；余额查询失败、格式异常或币种不匹配均不宣告恢复。整笔订单涉及的所有卡台均足够才进入 `ready`，邮件发到独立 `notifications` 队列。

状态为 `waiting → ready → sent`；已付款、主动取消、删除、邮箱变化等不再适合通知的订单转 `closed`。等待本身不创建采购、不创建支付、不改变订单或钱包，不冻结或预留卡台资金。客户回来付款仍经过原有检查。

过期自动取消的订单仍可收到返回商城提醒，不恢复旧订单。识别依据为 `canceled_at >= expires_at`；有效订单可继续付款，过期后重新下单。邮件统一进入商城首页，不把游客密码或登录凭据放入链接。已付款及退款订单不发送本类邮件。

## 去重、重试和可观测性

同一订单只登记一次；定时任务和邮件任务在 Redis 去重，实际发送再通过数据库的两分钟租约防止多个 worker 同时发送。SMTP 请求沿用现有 15 秒总超时。邮件积压超过余额快照有效期（90 秒）时，返回等待状态，重新查询后再发；下一轮查询发现余额再次不足，也会撤销尚未开始发送的恢复通知。

发送失败后至少等待一分钟，再检查余额、重新入队。队列丢失或不可用时保留数据库记录，下一轮恢复。成功后持久化 `sent_at`，后台通知中心记录 `exception_alert / supplier_balance_recovered` 的每次实际发送结果；重复任务会查询成功记录，不重复发送。SMTP 已接受但日志写入失败时仍将等待记为成功，并向任务日志报告审计错误。

SMTP 与数据库之间不能组成原子事务：极端情况下，SMTP 已接受且进程在成功落库之前崩溃，仍存在重复送达窗口。SMTP 接受也不代表客户收件箱已收到或已阅读。卡台余额没有冻结能力，多位客户同时回来付款时继续由原付款检查保护。
