# 邮件时效维护

目标为业务事件触发后一分钟内通知。此前成交通知为了等待采购摘要，最多延后十分钟；早期 `fulfilled` 状态未识别又导致已发货订单也等待完整时限。状态识别已在前次发布修复，本次将等待限制与其他邮件通道一起调整。

## 发送路径

- 商家成交、余额不足及其他通知中心邮件，客户订单付款、交付和退款邮件使用 `notifications` 队列，四个专用处理位置。采购、库存及结算任务不能占用这些位置；原 `default` 队列中的历史邮件仍可被旧消费者读取。
- 成交摘要最多等待约五秒，按初次入队时间计算，等待重投为两秒，延时任务每秒检查。上游余额查询共用三秒预算，查询失败仍发提醒并明确标注，不伪造零余额或采购成功。
- 邮件任务失败后的间隔为 3、5、10、20、30 秒；只更改邮件任务策略，采购任务继续原策略。通知按业务和收件人记成功，已成功收件人不会因为其他收件人失败再次发送；余额不足邮件也使用同一事件快速重试。
- 所有 SMTP 邮件共用十五秒连接及协议总超时，覆盖验证码、通知、订单、附件和测试邮件。服务器接受正文后，QUIT 失败只记连接清理错误，不把已接受邮件重发。
- 验证码仍同步发送，保持验证码时效、发送额度、图形验证码与其他防刷限制。原有场景开关、商家收件人和客户邮件开关保留。

`smtp_send_complete` 日志记录 Message-ID、接受/失败状态和耗时，不记录正文、验证码、卡密或密码。通知中心成功记录的时间为发送服务接受完成时间。收件箱到达应另核对邮件的 Received 时间或收件箱记录，不能用仅入队成功代替已收到。

一分钟是正常服务器、网络及邮箱服务条件下的交付目标；第三方停机、限流、垃圾邮件拦截或手机推送延迟不能由本站绝对保证。失败仍保留日志与重试，不能为满足时间数字而记为成功。

## 不扣款测速

`cmd/mail-latency-check` 默认只读检查，SQLite 用 `mode=ro`。明确传 `-send` 与唯一 `-token` 时，向当前唯一商家收件人发三封标记为测试的邮件：通过正式通知队列的一封、使用同一验证码发送器的一封、使用同一订单附件发送器的一封。验证码不落库、没有有效卡密，不创建订单，不启动应用业务组件，不调用付款或采购。相同队列测试标识不可重复入队。

示例（在正式发布目录使用现有私有配置）：

```sh
./mail-latency-check -config /srv/zhixiang/shared/config.yml
./mail-latency-check -config /srv/zhixiang/shared/config.yml -send -token MAIL-YYYYMMDD-HHMMSS
```

测试覆盖普通工作者被占满、一次发送失败后快速恢复、五秒采购摘要上限、慢余额接口、已成功收件人去重、正文已接受但 QUIT 断开，以及十一种 SMTP 邮件路径。测试仅使用临时 Redis、模拟 SMTP、模拟上游及临时数据库；真实测速只向已授权商家邮箱发送。

测速工具查询日志时将 JSON 值显式转换为文本，兼容应用保存的 SQLite BLOB，避免邮件已收到却误报超时或遗漏重复发送检查。所有测试邮件标题含测试标识，交付邮件使用专属测试模板，不修改站点模板。

2026-10-16 本机日常后端配合回环 SMTP 完成端到端补测：正常成交队列约 204 毫秒；一次临时 SMTP 拒收后约 2485 毫秒成功。验证码和交付附件也实际收到，同一测试标识再次执行被拒绝；临时邮件设置已精确恢复。上述为本机结果，不能代替正式邮箱收件时效验收。
