# USDT / BNB Smart Chain 收款

本模块直接监听链上转账，通过原支付服务完成订单入账，再触发原有套餐卡密交付。它不托管钱包、不发送链上交易，也不要求收款钱包私钥或助记词。

## 固定配置

- 网络：BNB Smart Chain 主网，chain ID `56`（BEP-20）。
- 收款地址：`0x66a8bab15067eab1efc948ac03684f0397c8416f`。
- 代币合约：`0x55d398326f99059ff775485246999027b3197955`，精度 18。仅认可这一合约，不能用代币名称判断。区块浏览器也可能将其显示为 Binance-Peg BSC-USD。
- 汇率：`1 USDT = 6.66 CNY`。当前仅支持人民币订单，汇率在创建支付单时保存。已有支付单不会随配置变更重新报价。

## 如何识别订单

共享收款地址无法从普通转账中读取商城订单号，所以每份支付单使用独立的精确金额：先将 `人民币应付金额 ÷ 6.66` 向上取到两位小数，再加 `0.000001` 到 `0.009999` USDT 的识别尾数，最终显示六位小数。

例如 133.20 元的基准金额是 20 USDT，实际支付页可能显示 20.003517 USDT。客户必须按页面完整金额到账，不能抹掉尾数；提现平台手续费应由客户另行承担。原订单与支付账本保留人民币金额，链上金额单独按 18 位精度整数保存，避免两位小数账本截断或浮点误差。

数据库保证同一网络、代币、地址的金额不重复分配。过期支付单的金额也不重新分配，防止迟到款被认成新订单。每个基准金额最多分配 9,999 个独立金额，容量耗尽时拒绝创建，不覆盖历史记录；大规模运营应扩展按订单独立地址的收款方案。

## 启用与运行

在服务器 `config.yml` 设置：

```yaml
bsc_usdt:
  enabled: true
  recipient: "0x66a8bab15067eab1efc948ac03684f0397c8416f"
  cny_per_usdt: "6.66"
  confirmations: 15
```

示例配置默认关闭，避免部署未经验收就开始收款。启用后自动创建一个 `USDT · BNB Smart Chain (BEP-20)` 支付渠道，可在原渠道管理中控制是否对客户开放。支付渠道的 provider 为 `bscusdt`，channel 为 `usdt-bep20`，交互方式为 `qr`，仅用于商城订单，不开放钱包充值。地址、汇率和确认数由以上服务器配置管理。

API 和 worker 实例必须使用相同配置及数据库。运行 `all`，或同时运行 `api` 和 `worker`；仅启动 API 不会持续监听。监听每 10 秒执行一次，每次最多扫描 100 个区块；保存的游标用于重启恢复。多个 worker 通过数据库原子更新协调。

默认 RPC 为 `https://bsc-rpc.publicnode.com`。可用服务端环境变量 `BSC_RPC_URL` 覆盖，支持含 API key 的 HTTPS URL，地址不会返回客户端或写入错误日志。服务必须支持 `eth_chainId`、`eth_call`、`eth_getBlockByNumber`（含 `finalized`）、`eth_getLogs`、`eth_getTransactionReceipt`。公开 RPC 有限流和可用性限制，正式运营需监控扫描进度并按负载换成稳定服务。

若停用收款，先在后台关闭渠道，继续运行监听器处理已展示给客户的支付单；不要直接删除历史游标、收款记录或金额占用记录。更换收款地址前应处理完旧地址的在途收款，本版本的单个监听实例只处理配置的那个地址。

## 付款确认与发卡

1. 读取并核验主网 chain ID 和目标合约精度。
2. 从持久化游标扫描指定合约的 `Transfer` 事件，限定收款地址。
3. 同时满足至少 15 个区块确认和 RPC `finalized`，核对区块 hash、成功交易回执和原始事件。
4. 按精确到账金额匹配支付单，要求转账区块在支付单生成以后、链上时间不晚于订单截止时间。
5. 转账凭据及待入账任务与扫描游标一起提交；使用 `chain + tx hash + log index` 去重。
6. 调用原支付服务，核对支付单原始人民币金额及币种，更新订单。符合兑换商品绑定的已付款订单随后自动发卡密。

RPC 错误、未确认交易、错误合约、错误收款地址、已移除事件和失败回执都不会使订单入账。错误页不会推进游标。已扫描区块的 hash 变化会停止推进并记录错误，需要人工核查。到账后写订单遇到临时错误时保留任务重试；不会依赖浏览器按钮或外部伪造回调确认付款。

监听从首次支付单创建时的区块之后开始，不会把地址的历史余额或历史入账当成新订单支付。

## 异常与后台查询

金额不完全相等（少付、多付或分笔）、截止后到账、同一支付单重复转账等记录为 `manual_review`，不会自动发第二份卡密，也不会自动链上退款。管理员核对原订单和链上记录后处理。订单已关闭、退款或支付状态有冲突的情况继续遵守原支付服务的异常账务规则。

查询接口位于现有后台 JWT、RBAC 和支付声明保护之下，`finance` 角色拥有只读权限：

- `GET /api/v1/admin/chain-payments/bsc-usdt/status`：扫描游标、最后推进时间、地址、汇率、待入账数与待核查数。
- `GET /api/v1/admin/chain-payments/bsc-usdt/transfers?state=manual_review`：转账证据，最多 100 条；可用 `before_block` 查询更早区块。

目前提供查询 API 和原支付/订单管理，未增加专门的链上对账管理页面。监控应关注 `bsc_usdt_listener_pass_failed` 日志、游标长期不推进及待入账记录积压。

## 验证范围

本地测试覆盖六位金额与汇率锁定、并发创建、确认数与最终确认、RPC/回执/区块校验、重复及迟到款、游标恢复、入账任务恢复，以及真实数据库中的“游客订单 → 链上确认 → 订单付款 → 交付唯一套餐卡密”。

支付、兑换、应用装配、数据库迁移及项目分层回归通过；前端 70 项测试与生产构建通过。本机缺少 CGO 编译环境，原有支付声明中间件中 3 个依赖 CGO SQLite 的测试未执行；同组不依赖该环境的空服务测试单独通过。

已对默认公共 RPC 进行只读连通性检查，验证主网、最终确认区块、18 位精度和目标地址日志查询。尚未部署持续运行，也未进行真实资金的小额验收。
