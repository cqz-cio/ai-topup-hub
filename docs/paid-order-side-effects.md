# 已付款订单历史副作用补齐

## 资金操作限制

2026-10-16 用户明确撤销此前的自动采购授权，要求不再扣上游余额。正式服务已增加 `90-no-purchase.conf`，强制 `UPSTREAM_PURCHASE_ENABLED=false`。发布、重启、回退都必须保留此文件并检查进程环境；未经用户重新明确授权，不得恢复自动采购。库存和余额的只读查询可以继续。

此前死锁修复重启恢复了一笔原有采购任务并实际扣款；“没有做扣款测试”不代表“没有发生采购扣款”。后续核验必须分别检查采购记录和上游余额，不能仅凭采购总数没增加判断未扣款。

## 修复范围

原死锁发生于采购任务创建之后、销售通知及累计消费统计之前。重启后采购恢复不会自动补齐这些后续步骤。已成功支付的重复回调只更新回调元数据，也不会重跑后续业务钩子。

`cmd/paid-order-repair` 是独立维护程序，不初始化应用容器、定时任务或采购服务。默认只读，应用时要求采购环境变量明确为 `false`。

- 读取经审核的两笔订单计划；核对用户、订单号、金额、原支付 ID、已付款和已交付状态、原采购完成状态以及该用户全部已付款父订单集合。
- 在单事务中将原为零的 `users.total_spent` 比较后设置为这两笔订单合计。只写该统计列，不修改余额、充值、佣金、付款、采购或交付记录。本次没有会员等级配置；若存在等级则拒绝执行，另行审核。
- 事务提交后只入队 `notification:dispatch` 销售通知，使用现有商家邮箱和模板。每笔订单固定任务 ID，保留 30 天；不启用 `Force`。既有成功通知日志、Redis 发送锁和发送成功标记继续防重。
- 队列故障后可重复同一计划：统计不会累加，已入队或已成功发送的邮件不会再次创建。命令成功表示任务入队；还必须核对通知日志的实际发送结果。

通知采购摘要同时识别实际采购终态 `fulfilled`，不再将已发货采购误判为待处理，并展示原采购金额。余额仍只经 `Ping` 查询。

## 使用和验证

先停止自动采购并确认没有未完成采购，备份线上库和服务配置，记录钱包流水、采购记录、上游余额及全部表摘要。计划包含 `incident`（固定为 `2026-10-16-paid-order-deadlock`）、`user_id`、`before`、`after`，以及两个具有 `id`、`order_no`、`payment_id`、`amount` 的 `orders`。

```sh
UPSTREAM_PURCHASE_ENABLED=false ./paid-order-repair -config /srv/zhixiang/shared/config.yml -plan /private/reviewed-plan.json
UPSTREAM_PURCHASE_ENABLED=false ./paid-order-repair -config /srv/zhixiang/shared/config.yml -plan /private/reviewed-plan.json -apply
```

测试使用隔离 SQLite 和假通知队列，覆盖只读预览、重复执行、部分入队失败后恢复、成功邮件跳过、统计冲突、未付款、退款、不同客户、付款失败、采购未完成、订单集合变化、会员等级和通知配置变化；拒绝时检查全部业务表不变。供应商适配器已有关闭采购时不产生任何 HTTP 请求的测试。

XorPay 已收款但通知失败的原订单，应在平台后台使用“再次通知”，让平台重新签名并确认 HTTP 应答；不得创建新支付、补扣、退款或改写本地付款状态。操作前再次核对采购关闭，之后核对平台状态、原支付资金字段、采购与余额。其他链扫描和公开接口继续只读检查，不进行实际扣款测试。

私有证据和本次计划保存在外层 `deployment/local/paid-side-effects/`，不提交凭据、数据库、收件地址、卡密或业务原始内容。
