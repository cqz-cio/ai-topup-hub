# 应用层防刷与资源保护

本次保护针对恶意注册、撞库、验证码邮件滥用和应用请求耗尽。它不能吸收打满服务器带宽的 DDoS；正式站仍需要边缘防护、源站访问限制和监控。本次仅实现代码及本地验证，生产生效状态以发布记录为准。

## 默认限制

配置位于 `security.abuse_protection`，示例见根目录 `config.yml.example`。未配置或值小于等于零时使用安全默认值；修改后需要重启后端。相应环境变量以 `SECURITY_ABUSE_PROTECTION_` 开头。

| 范围 | 默认值 | 计数方式 |
| --- | --- | --- |
| 商城 API 总入口 | 240 次/分钟 | IP，包含公开及用户接口 |
| 注册、登录等认证入口 | 30 次/分钟 | IP |
| 图形验证码 | 20 次/分钟 | IP |
| 发验证码、提交注册、找回密码 | 合计 5 次/分钟 | IP |
| 登录密码 | 沿用 `login_rate_limit`，默认 5 次/300 秒，超额阻断 900 秒 | 新增独立邮箱桶，保留原邮箱 + IP 桶 |
| 用户写入操作 | 30 次/分钟 | 用户 ID，换 IP 不重置 |
| 登录态换邮箱 | 5 次/分钟 | 用户 ID |
| 验证码邮件 | 同邮箱 10 封/小时、30 封/24 小时；全站 300 封/小时、2000 封/24 小时 | 所有用途共享，窗口从首个预占开始 |
| 同邮箱发送间隔 | 沿用 SMTP 设置，默认 60 秒 | 所有用途共享 |

商城单进程最多同时处理 64 个请求，其中认证入口最多 16 个（可配置）。后台公开登录单独允许 8 个并发、30 次/分钟/IP 的入口额度，并保留原 IP 登录限制，增加用户名限制。额度统计的是请求次数，包含成功和失败，适用正常操作量的小型商城；活动或共享网络用户多时，应按实际指标调参。

普通商城请求体最大 1 MiB，用户及后台公开认证请求最大 64 KiB；无 Content-Length 的请求同样受限。认证保护不改变后台上传额度。超大请求返回 HTTP 413，频率超限返回 HTTP 429 并提供 `Retry-After`，并发满载返回 HTTP 503。

支付回调保持独立的 120 次/分钟/IP 规则，默认支付回调和自定义回调都受保护，各自的单进程并发上限为 16、请求体上限为 4 MiB；商城用户的配额不会占用回调配额。回调验签、支付幂等及采购逻辑保持原行为。

## 发信和验证码

- 匿名 `/api/v1/auth/send-verify-code` 只接受 `register` 和 `reset`。`change_email_old`、`change_email_new` 必须走现有登录态 `/api/v1/me/email/send-verify-code`；匿名 `telegram_bind` 也被拒绝。现有 Telegram 登录与登录态绑定保持原入口。
- 邮箱只接受规范的单一地址，统一大小写与首尾空白，拒绝显示名称、尖括号包装及超长地址，防止同一邮箱以不同形式绕过额度。不对各邮箱服务商的加号别名作不可靠的统一合并。
- 在实际 SMTP 操作之前，原子预占邮箱冷却、小时/日额度及全站额度。并发请求、切换用途或 IP 不会多次取得发送资格；SMTP 失败或结果未知也保留已预占额度，避免失败重试风暴。
- Redis 配置启用时，发信额度存储故障返回 HTTP 503，停止发信。只有明确关闭 Redis 的单进程本地模式使用有容量上限的内存计数。多实例生产必须使用同一个持久化 Redis、DB 与 Prefix；内存模式重启会丢失额度。
- 验证码消费和尝试计数在数据库中原子更新。只有最新、未过期、未使用、尚有尝试额度的验证码能成功消费一次；并发错误尝试不会超出尝试预算。
- SMTP 连接建立最多 10 秒，连接、握手、发信和退出总计最多 30 秒。此超时同样保护经营者通知发送，验证码邮件额度不计入成交通知。

## 订单风控与发布注意

后台已启用的订单频率规则在 Redis 缺失或异常时停止放行，返回可重试的错误；未启用的业务风控设置保持原值。对启用了订单限流的环境，Redis 是必要依赖。不要通过关闭邮箱验证、清空 Redis 或放开所有代理来源来处理误拦截。

应用普通请求限流保留 Redis 故障时的进程内兜底；验证码邮件与已启用订单风控更严格，故障时停止对应操作。普通限流兜底只能限制单个实例。重试时应尊重 `Retry-After`，避免客户端自动高频重试。

部署前按 `docs/release-process.md` 备份并发布已验证后端，无需复制本机数据库或开启新业务渠道。反向代理必须正确传递客户端 IP，应用只信任明确的代理地址；CDN 接入后需要同步调整可信代理和源站 ACL，否则会误把整站用户计成同一 IP 或允许伪造 IP。

建议监控 429/503 数量、认证耗时、验证码邮件发送量、SMTP 失败率、Redis 可用性及数据库等待。上线后根据正常高峰校准配额；本地并发回归不代表正式站 QPS 或 DDoS 承载量。

## 验证方式
